# Развёртывание devBIM Web на отдельной машине

Назначение: перенести деплой dsh web (бренд devBIM, публичный адрес через туннель
Cloudflare) с рабочей машины на отдельную машину, чтобы выдать клиенту ссылку для
тестирования и не открывать рабочую машину. Документ рассчитан на
агента-установщика: выполняйте шаги по порядку, в точках решения (шаг 0) спросите
оператора, при расхождении с реальностью остановитесь и переспросите.

Принцип: демо-машина — расходная. На неё переносят код и расходные ключи.
Личные данные, история сессий и основные API-ключи остаются на рабочей машине.

## Что переносится и что не переносится

Переносится: код ветки `internet`, портативный Node (`.tools/node` целиком),
конфиг туннеля Cloudflare, конфиг модели и credential-хранилище модели
(`~/.dsh/settings.yaml`, `~/.dsh/.credentials.yaml` — желательно с новым
расходным ключом).

Не переносится никогда: `Harness/.env` с рабочей машины (на демо-машине он
создаётся заново, шаг 5), `~/.dsh/sessions/`, `~/.dsh/cache/`,
`~/.dsh/dsh-runtimes/`, `~/.dsh/storages/`, `~/.dsh/attachments/`,
`~/.dsh/.agent-presets/`, `~/.dsh/skills/`.

## Шаг 0. Точки решения — спросить оператора до начала

1. Способ получения кода: `git clone` из origin (нужен выполненный заранее шаг 1)
   или копия папки без `node_modules`, `.git`, `coverage`, `.env`.
2. Туннель: перенести существующий туннель `devbim` (адрес `devbim.dev-bim.com`;
   на время демо туннель на рабочей машине не запускать — у одного имени туннеля
   должен быть один активный коннектор) или создать отдельный туннель
   `devbim-demo` (адрес `demo.dev-bim.com`; машины независимы). Рекомендуется
   отдельный туннель.
3. drawing5: нужен ли клиенту доступ к чертежам (MCP-сервер на `127.0.0.1:8808`).
   Если нет — блок `mcp-drawing5` удаляется из `devbim.patch.yml` (шаг 8). Если
   да — на демо-машине дополнительно разворачивается сам drawing5-сервер, это
   отдельная задача вне этого документа; перенесите тогда и `DRAWING5_KEY`.

## Шаг 1. Рабочая машина: опубликовать ветку (один раз)

На рабочей машине в корне репозитория:

```sh
git push -u origin internet
```

На origin сейчас есть только `master`; вся devBIM-настройка (бренд, туннель,
drawing5-MCP, лаунчеры) живёт в локальной ветке `internet`. Пока она не запушена,
клонировать на демо-машине нечего. `.env` и личные данные в git не входят — пуш
их не публикует.

## Шаг 2. Окружение и код

Окружение демо-машины: Windows 10/11, ~10 ГБ свободного места, исходящий интернет
(туннель работает только на исходящие соединения, пробрасывать порты не нужно).
Из инструментов нужны только два; если отсутствуют, установите:

```sh
winget install Git.Git
winget install Cloudflare.cloudflared
```

Больше ничего ставить не нужно. Node приезжает с рабочей машины (шаг 3), pnpm
ставит corepack из портативного Node (шаг 4). Нативная сборка (Visual Studio
Build Tools, Python) деплою не требуется: компилируемых `.node`-аддонов в дереве
нет, а pnpm 11 по умолчанию блокирует install-скрипты зависимостей.
`install_tools.bat` внутри `.tools/node` — установщик тулчейна для сборки нативных
модулей, для работы деплоя не нужен. `DEEPSEEK_API_KEY` тоже не нужен: модель
работает через credential-хранилище (шаг 6).

Получить код:

```sh
git clone -b internet https://github.com/devbim26/deepseek-harness.git C:\dev\harness
```

Путь без кириллицы и пробелов рекомендуется (`C:\dev\harness` — хороший вариант);
кириллица в пути на рабочей машине — историческая причина, а не требование.
Если git-доступа нет — скопируйте папку репозитория с рабочей машины, исключив
`node_modules`, `.git`, `coverage`, `.tools` (Node переносится отдельно), `.env`.

## Шаг 3. Портативный Node

Скопируйте с рабочей машины папку `.tools/node` целиком в `C:\dev\harness\.tools\node`
(около 200 МБ; флешка или сетевая папка). Требование версий: Node `^22.19 || >=24`;
проверьте:

```sh
C:\dev\harness\.tools\node\node.exe --version   # ожидается v24.x
```

`install_tools.bat` внутри этой папки не запускайте: он ставит Python и Visual
Studio Build Tools для компиляции нативных модулей, для работы деплоя это не
нужно.

## Шаг 4. Зависимости и сборка

Из корня репозитория (`C:\dev\harness`):

```sh
".tools\node\corepack.cmd" pnpm install
".tools\node\corepack.cmd" pnpm run build
```

`packageManager` закреплён (`pnpm@11.7.0`) — corepack поставит именно его, глобальный
pnpm не нужен. Сборка обязательна: `lib/`, `apps/web/dist/` и `*.tsbuildinfo` не
хранятся в git, а `dsh web` работает по собранным артефактам. Первая установка и
сборка занимают несколько минут.

## Шаг 5. Новый .env

Создайте `C:\dev\harness\.env` (рядом с `dsh-web.cmd`; образец полей — `.env.example`):

```sh
DEVBIM_WEB_PASSWORD=<новый пароль, который вы отдадите клиенту>
DRAWING5_KEY=<только если drawing5 нужен на демо-машине>
```

Рабочий `.env` не копируйте: пароль должен быть одноразовым, а ключ drawing5 на
демо-машине — расходным.

## Шаг 6. Конфиг модели (~/.dsh)

`~/.dsh` на демо-машине создаётся сам при первом запуске. С рабочей машины
перенесите только два файла: `~/.dsh/settings.yaml` (если существует) и
`~/.dsh/.credentials.yaml`. Историю сессий и кэши не переносите (список — в начале
документа). Рекомендуется вместо копии `.credentials.yaml` внести туда новый
расходный ключ модели по образцу секции `refs:` рабочего файла.

## Шаг 7. Туннель Cloudflare

`cloudflared.exe` должен быть доступен в `PATH` (установка: `winget install Cloudflare.cloudflared`
или одиночный бинарник в `%USERPROFILE%\.cloudflared\`). Туннелю нужен только
исходящий интернет — пробрасывать порты на роутере не надо.

Вариант A — перенести существующий туннель `devbim`:
скопируйте с рабочей машины `%USERPROFILE%\.cloudflared\config-devbim.yml` и файл
credentials туннеля (путь указан в `credentials-file` конфига). Конфиг уже
указывает `devbim.dev-bim.com → http://127.0.0.1:3080`. На рабочей машине на время
демо туннель не запускайте (`dsh-web.cmd stop` гасит и сервер, и туннель).

Вариант B — отдельный туннель `devbim-demo` (рекомендуется):

```sh
cloudflared tunnel login                          # браузер, зона dev-bim.com
cloudflared tunnel create devbim-demo             # печатает UUID
cloudflared tunnel route dns devbim-demo demo.dev-bim.com
```

Создайте `%USERPROFILE%\.cloudflared\config-devbim.yml` (имя файла именно такое —
лаунчер ищет его по этому имени) с новым UUID из `create`:

```yaml
tunnel: <UUID из tunnel create>
credentials-file: C:\Users\<пользователь>\.cloudflared\<UUID>.json
ingress:
  - hostname: demo.dev-bim.com
    service: http://127.0.0.1:3080
    originRequest:
      noTLSVerify: true
  - service: http_status:404
```

В варианте B туннель запускайте отдельно (лаунчер поднимает туннель только с
именем `devbim`): скопируйте `run-tunnel-devbim.bat` в `run-tunnel-devbim-demo.bat`
и замените в последней строке `run devbim` на `run devbim-demo`. Запущенный так
коннектор `dsh-web.cmd` не задублирует (он ищет работающий `cloudflared` по
подстроке `config-devbim`), а `dsh-web.cmd stop` его же и погасит. В `service`
указывайте `127.0.0.1`, не `localhost`: cloudflared иначе пробует IPv6 `::1`.

## Шаг 8. drawing5

drawing5 подключает плагин `dsh-plugin-drawing5` (MCP-инструменты и окно
«Чертежи»); блоки `- id: drawing5-mcp` и `- id: drawing5-skill` в
`packages/bundle/web-app/devbim.patch.yml` переопределяют строки плагина на
деплой-значения: локальный сервер и токен из `DRAWING5_KEY`.

Если оператор ответил «не нужен» (шаг 0.3) — удалите эти два блока из
оверлея и не ставьте плагин в веб-профиль. Правка локальная, не коммитьте
её. Если нужен — разверните drawing5-сервер (отдельная задача) в режиме
`cloud`, выпустите лицензию (`python -X utf8 -m cloud.issue_license`) и
запишите её токен в `DRAWING5_KEY` (Harness/.env), затем поставьте плагин в
веб-профиль: pnpm add tgz-сборки в `~/.dsh/profiles/web` и
`dsh-plugin-drawing5` в `dsh.profile.bundles` профиля. Блоки оверлея
оставьте как есть.

Сметный сервер (плагин `dsh-plugin-smeta`) на демо-машине разворачивать не
нужно: его адрес приходит из `SMETA_SERVER_URL` (по умолчанию
`https://smeta.dev-bim.com`), а сам сервер живёт на своей машине за туннелем.
Локальный адрес `127.0.0.1:8021` больше не действует.

## Шаг 9. Запуск и проверка

```sh
dsh-web.cmd start
```

Лаунчер поднимает сервер (порт 3080), открывает браузер и печатает токен-ссылку;
в варианте A он же поднимает туннель. Проверки по порядку; остановитесь на первом
расхождении:

```sh
netstat -ano | findstr ":3080" | findstr LISTENING   # сервер слушает
curl -s -o nul -w "%{http_code} -> %{redirect_url}" http://127.0.0.1:3080/
  # ожидается 303 -> .../devbim/login
curl -s -o nul -w "%{http_code}" http://127.0.0.1:3080/devbim/login   # 200
curl -s -o nul -w "%{http_code}" https://demo.dev-bim.com/devbim/login  # 200, вариант B
```

Затем в браузере: открыть публичный адрес, ввести пароль из шага 5 — вход должен
перебросить на токен-ссылку и показать приложение.

## Шаг 10. Проверка модели

В приложении отправьте тестовое сообщение агенту. Если модель не отвечает:
проверьте выбор модели (`/model`) и наличие ключа в `~/.dsh/.credentials.yaml`
(шаг 6). Модель работает через ключ из credential-хранилища; `DEEPSEEK_API_KEY`
в `.env` не нужен.

## Известные ловушки

- Порт 3080 занят сторонним процессом — лаунчер предупредит; найдите процесс по
  `netstat -ano | findstr ":3080"` и освободите порт.
- Второй запуск `dsh-web.cmd` при работающем сервере не перезапускает его, а
  предлагает открыть браузер; перезапуск — `dsh-web.cmd restart`.
- Первый запуск после `pnpm install` занимает дольше обычного (сборка клиентских
  бандлов уже сделана на шаге 4; медленным бывает только холодный старт tsx).
- Если curl на публичный адрес даёт 502 — туннель ещё поднимается; повторите через
  5–10 секунд, затем проверьте окно/лог cloudflared.

## Гигиена после теста

- `dsh-web.cmd stop` гасит сервер и коннектор туннеля.
- Пароль из шага 5 считается раскрытым после теста — не используйте его больше нигде.
- Логи сессий клиента остаются в `~/.dsh/sessions/` демо-машины; при передаче
  машины дальше — удалите `~/.dsh` целиком.
- Если на демо-машину попал основной (не расходный) ключ модели — ротируйте его
  на стороне провайдера после теста.
