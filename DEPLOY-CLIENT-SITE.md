# Клиентский сайт devBIM: деплой north-waterfront

Назначение: отдельный веб-деплой `dsh web` для передачи клиенту («Северный берег»),
изолированный от внутреннего `devbim.dev-bim.com`: свой порт (3081), свой
`DSH_HOME` (сессии, креды, настройки), свой пароль входа и урезанный UI —
клиенту доступны только чат и окно «Чертежи». Внутренний сайт продолжает
работать на 3080 без изменений.

## Состав

Файлы в репозитории (ветка `webUI`):

- `packages/bundle/web-app/client-north-waterfront.patch.yml` — оверлей
  клиентского сайта: NW-бренд (пакет `ui-brand-north-waterfront`: бейдж NW и
  «north-waterfront» в сайдбаре и герое), парольный гейт `devbim-auth` с NW-копией
  входа (`entryTitle` «NW — вход», вордмарк NW) и титулом вкладки
  (`indexTitle` «NW — Северный берег», переписывается на каждый запрос — сборка
  отдаёт общий дефолт), модели (openrouter, ключ из клиентских кредов, список
  `NW_MODELS` вместо полного каталога), `trustedHosts` домена, отключения
  командных поверхностей UI, пресет агента
  «чертежи + чтение файлов» и режимы доступа, сжатые до одного `workspace-write`
  с закреплённым дефолтом (клиент работает в своей папке рабочей области,
  переключить режим нельзя), база проектов `projectBase` (кнопка «Новый
  проект», см. «Папки проектов») и spill-каталог в home деплоя вместо
  `%TEMP%`;
- `dsh-web-north-waterfront.cmd` — лаунчер: порт 3081, `DSH_HOME=%USERPROFILE%\.dsh-north-waterfront`,
  env из `.env.north-waterfront`, туннель `config-north-waterfront`; перед стартом возвращает
  `.tools\node\node.exe` метку целостности Medium — рабочая папка репозитория помечена Low
  песочницей `dsh-sandbox-windows-acl`, унаследованный Low-образ понижает процесс до Low
  integrity, и тот не может писать в `DSH_HOME` (EPERM на `profiles/web/cordis.yml`);
- `nw-models.cmd` — батник списка моделей: пишет `NW_MODELS` в env, показывает
  текущий список, сбрасывает (после сброса сайт не стартует, пока не записан
  новый список) и предлагает перезапуск;
- `.env.north-waterfront` — секреты сайта (в `.gitignore`): пароль входа,
  `DRAWING5_API_KEY`, `DRAWING5_SERVER_URL`, `SMETA_SERVER_URL`,
  `DOC6_API_KEY`, `DOC6_SERVER_URL`, `OPENROUTER_API_KEY` (ключ OpenRouter
  сайта), при необходимости `NW_MODELS`
  (список доступных в выборе моделей) и `ZAI_CODING_CN_API_KEY`
  (кодинг-подписка Z.AI, см. «Подписки по ключу» ниже).

Машинные артефакты:

- `%USERPROFILE%\.dsh-north-waterfront` — home клиента; профиль `web` с
  плагином `dsh-plugin-drawing5`; `.credentials.yaml` — копия внутренней с
  удалённой записью `client-connection/browser-session` (секрет(cookie) сайта
  свой, создаётся при первом старте);
- `%USERPROFILE%\.cloudflared\config-north-waterfront.yml` — туннель
  `north-waterfront` → `http://127.0.0.1:3081` (service строго `127.0.0.1`,
  не `localhost`).

## Развертывание нового клиента

1. Лицензия drawing5: `python -X utf8 -m cloud.issue_license --company "<клиент>"`
   из репозитория drawing5; токен — в `.env.<клиент>` как `DRAWING5_API_KEY`.
2. Домен и туннель: `cloudflared tunnel create <имя>`,
   `cloudflared tunnel route dns <имя> <домен>`,
   `config-<имя>.yml` по образцу `config-devbim.yml` (ingress: домен →
   `http://127.0.0.1:<порт>`).
3. Оверлей: скопировать `client-north-waterfront.patch.yml`, заменить домен в
   `connection`; список отключений и пресет агента — по образцу.
4. Лаунчер: скопировать `dsh-web-north-waterfront.cmd`, заменить `PORT`,
   `DSHHOME`, `ENV_FILE`, имя туннеля и аргумент `--port`.
5. Home: скопировать структуру `%USERPROFILE%\.dsh-north-waterfront`
   (профиль `web` + плагин из `drawing5/plugin/dsh-plugin-drawing5/dist`,
   креды без `client-connection/browser-session`).

## Запуск и проверка

```sh
dsh-web-north-waterfront.cmd start    # сервер 3081 + туннель
dsh-web-north-waterfront.cmd stop
dsh-web-north-waterfront.cmd restart
```

Только лаунчер: он читает `.env.north-waterfront` в окружение процесса.
Прямой запуск `pnpm dsh web --patch packages/bundle/web-app/client-north-waterfront.patch.yml`
env-файл не читает — оверлей упадёт при старте с пустым `NW_MODELS`
(такая защита появилась после инцидента с ручным запуском, когда пикер
тихо показывал дефолтные три модели).

Чек-лист: `http://127.0.0.1:3081/` даёт 303 → `/devbim/login`; неверный
пароль — 401; верный — вход. Страница входа: титул «NW — вход», вордмарк NW.
После входа: бейдж NW и «north-waterfront» в сайдбаре, титул вкладки
«NW — Северный берег»; devBIM нигде не виден (внутренний сайт на 3080
продолжает показывать devBIM). В UI: чат отвечает, «Чертежи» показывает дерево
клиента; выбор модели есть, но показывает только `NW_MODELS` (настройки,
Plugins, терминал и файлы отсутствуют); список сессий пуст (изоляция от
внутреннего сайта). Чип режима агента доступен:
штатный «Стандартный» и пункт «Свой агент» (конструктор кастомных агентов,
см. ниже); селектор режима возле «+» и команда Permission внутри «+»
показывают единственный режим «Запись в рабочей области» (Workspace Write).
Кнопка «Новый проект» в заголовке панели проектов создаёт папку
`%USERPROFILE%\north-waterfront\<имя>` и открывает сессию в ней; повтор
того же имени даёт в диалоге «Папка с таким именем уже существует.».
Публично: тот же чек-лист через домен туннеля.

## Выбор модели

Пикер модели (`ui-model-selection`, `/model` и кресло модели в композере)
включён, но каталог OpenRouter заменён списком `NW_MODELS` из
`.env.north-waterfront` — клиент видит и может выбрать только эти модели.
Без переменной (или с пустой) старт падает громкой ошибкой: список приходит
только из env лаунчера, и его отсутствие означает запуск мимо
`dsh-web-north-waterfront.cmd` (исторический тихий фоллбэк на три модели
маскировал такие запуски). Задать список можно строкой:

```ini
NW_MODELS=deepseek/deepseek-v4.1-flash,deepseek/deepseek-v4-pro,deepseek/deepseek-v4-flash
```

Список можно менять батником `nw-models.cmd` (рядом с лаунчером):

```sh
nw-models.cmd "deepseek/deepseek-v4.1-flash,deepseek/deepseek-v4-pro"
nw-models.cmd show     # показать текущий список
nw-models.cmd reset    # удалить NW_MODELS, вернуть дефолт оверлея
```

Правила:

- первая модель списка — дефолт для новых сессий; остальные — варианты выбора;
- id — из каталога OpenRouter, встроенного в pi-ai; модель вне каталога
  даст диагностику при запросе;
- список читается при старте: после правки `.env.north-waterfront` нужен
  перезапуск (`dsh-web-north-waterfront.cmd restart`);
- `ui-settings-models` остаётся отключённым, поэтому клиент не может добавить
  провайдера или расширить список через настройки; нативные DeepSeek-адаптеры
  в оверлее отключены, чтобы в пикере не появились их несокращённые каталоги;
- выбор проверяется на Host (`session.selectModel` → `modelAvailable`), поэтому
  модель вне списка отклоняется с `session/model-unavailable`, даже если её
  попытаться выбрать в обход UI;
- пустой или незаданный `NW_MODELS` — ошибка старта с подсказкой про лаунчер,
  а не тихий дефолт: защита от запуска напрямую `pnpm dsh web --patch …`,
  при котором env-файл лаунчера не читается.

Уже созданные сессии сохраняют модель, с которой начаты; новый список
действует на новые сессии и на явный выбор в существующей.

## Подписки по ключу

Кроме OpenRouter сайт может ходить в подписочные провайдеры напрямую: ключ в
`.env.north-waterfront` подключает маршрут, и его каталог появляется в пикере
отдельной группой. Поддерживается встроенный в pi-ai провайдер
`zai-coding-cn` — кодинг-подписка Z.AI (bigmodel.cn):

```ini
ZAI_CODING_CN_API_KEY=<ключ подписки>
```

- ключ читается при старте лаунчером, как и остальные секреты; после правки
  нужен перезапуск (`dsh-web-north-waterfront.cmd restart`);
- непустой ключ добавляет маршрут `zai-coding-cn` (в пикере — группа
  «Z.AI Coding»): модели `glm-5.3`, `glm-5.3-flash`, `glm-5.3-highspeed`,
  `glm-4.6v`, эндпоинт `https://open.bigmodel.cn/api/coding/paas/v4` и
  протокол наследуются из каталога pi-ai, в оверлее ничего править не надо;
- пустое или отсутствующее значение — маршрут не создаётся вовсе: маршрут без
  ключа всё равно показал бы каталог, и каждый запрос клиента падал бы;
- международная подписка (api.z.ai) подключается тем же способом с другими
  именами: переменная `ZAI_API_KEY`, маршрут `zai` (каталог шире — glm-4.7,
  glm-5-turbo, glm-5.2*); правка — в блоке `llm-pi-ai` оверлея;
- запросы идут ключом подписки и тарифицируются ею, а не OpenRouter; модели
  из `NW_MODELS` продолжают ходить через OpenRouter, поэтому продублированные
  там `z-ai/*` id можно сократить, если подписка покрывает их.

`OPENROUTER_API_KEY` в том же файле — ключ OpenRouter самого сайта: если он
не задан в env, ключ берётся из хранимых кредов `DSH_HOME`
(`.credentials.yaml`, ref `OPENROUTER_API_KEY`).

## Свои агенты (кастомные пресеты)

Пользователи сайта создают своих агентов через пункт «Свой агент» в чипе
выбора режима (над полем ввода на пустой сессии): имя, описание, инструкция
и выбор инструментов из whitelist. Записи хранятся как данные в
`%USERPROFILE%\.dsh-north-waterfront\storages\` (домен `custom_agent_presets`,
json — по одному файлу на запись) и монтируются в реестр пресетов как
`custom/<slug>`; выбор и смена — штатным чипом до первого сообщения сессии.

Границы безопасности: пользовательский ввод превращается только в значения
типизированной конфигурации (никакого YAML/кода от пользователя Loader не
получает); каждому агенту подставляется префикс-персона сайта; фиксированные
базовые строки (инструкции, время, компактация, read-only чтение файлов
`read`/`grep` с путём, ограниченным рабочей папкой сессии, доставка файлов
`present`) копируются оверлеем из
`preset-standard`; инструменты — только чекбоксы из
`allowedTools` оверлея (`Вопросы пользователю`, `Задачи`, `Отчёт PDF`,
`Чертежи (drawing5)`, `Сметы (БелЕНиР)`, `Нормы (doc6)`). Отмеченный чекбокс
монтирует строку в агента, снятый — жёстко блокирует: строки MCP
drawing5/smeta/doc6 отключены на host-plane и монтируются только внутри
выбранного агента.
`Отчёт PDF` монтирует `pdf_report`: агент собирает отчёт из текста, таблиц
и изображений и отдаёт готовый файл через базовую строку `present`.
Расширять whitelist — только после ревью песочницы добавляемых строк.
Лимиты (длина инструкции 16384 символов, до 50 агентов на сайт) и список —
в конфиге `agent-preset-custom` того же оверлея. Список общий на весь сайт
(вход по одному паролю, identity нет): правка и удаление доступны всем
вошедшим.
Битая запись (нарушение схемы в файле) при старте уходит в бэкап с записью
в лог и в ростер не попадает.

Оркестраторы и видимость: чекбокс «Оркестратор» (доступен, пока оверлей
несёт поле `delegation` у `agent-preset-custom`) превращает агента в
верхнеуровневого: сервис монтирует в его пресет строку `tool-subagent`
с `allowedAgentPresets` — id агентов, отмеченных в секции «Запуск агентов»
(только обычные агенты, не другие оркестраторы и не сам агент). Оверлей
может задать `delegation.rosterTemplate` — подводку, после которой сервис
добавляет в промпт оркестратора ростер делегатов (id, имя, описание
каждого): модель знает, кого запускать и обязана передавать
`agent_preset`, без ручного перечисления агентов в инструкции. Оверлей
может задать и `delegation.control` — дополнительную строку только для
оркестраторов; в NW это `@deepseek-ai/dsh-tool-subagent-control`:
оркестратор получает `list_agents`, `wait_agent`, `send_message` и
`interrupt_agent` и сам может перепроверять и прерывать зависших детей.
Чекбокс
«Показывать в выборе режима» прячет агента из пикера пресетов; скрытый
агент остаётся запускаемым оркестратором. Удаление агента каскадно
вычёркивает его из чужих списков запуска, правка — перемонтирует
ссылающиеся оркестраторы, чтобы ростер отражал актуальные имя и описание;
опустевший оркестратор сохраняет флаг, но строка делегирования не
монтируется. После обновления сайта перезагрузите открытые вкладки NW:
старый клиентский бандл не отправляет новые поля агента, и сохранение
будет отклонено до перезагрузки.

## Папки проектов

Кнопка «Новый проект» в заголовке панели проектов создаёт именованную папку
и воркспейс в ней; сессия открывается сразу в новой папке. Всё
пользовательское (отчёты PDF, вложенные папки, файлы сессий) пишется в папку
проекта; spill остаётся внутренним кэшем восстановления контекста модели и
в проекты не попадает.

Пути на диске — на машине лаунчера, под его учёткой:

- `%USERPROFILE%\north-waterfront` — база проектов; переопределяется
  переменной `NW_PROJECTS_DIR` в `.env.north-waterfront` (лаунчер задаёт
  дефолт до загрузки env-файла, поэтому файл всегда выигрывает);
- `%USERPROFILE%\north-waterfront\<имя>` — один проект = одна дочерняя
  папка базы; cwd сессий этого воркспейса — сама папка проекта;
- first-use дефолтный воркспейс свежего деплоя якорится в
  `<база>\default-workspace`; уже инициализированный дефолт в Documents не
  переносится и остаётся в панели как обычный воркспейс;
- `%USERPROFILE%\.dsh-north-waterfront\spill` — spill-файлы (вместо
  `%TEMP%\dsh-spill-*`), 30-дневная очистка без изменений.

Правила безопасности:

- имя проекта — ровно один безопасный сегмент каталога: 1–64 символа, без
  `/ \ < > : " | ? *` и управляющих символов, без `.` и `..`, без точки или
  пробела на краях, без зарезервированных имён Windows (CON, PRN, AUX, NUL,
  COM1–9, LPT1–9 в любом регистре); путь не может выйти за базу, и
  клиентский пользователь не получает браузинг файловой системы сервера;
- песочница не расширяется: действуют те же `workspace-write` + ask — запись
  ограничена cwd сессии, а cwd каждого воркспейса — его собственная папка;
- имя — типизированное значение формы, а не свободный путь; отказы громкие,
  с кодами `workspace/project-unavailable`, `-name-invalid`, `-exists`,
  `-create-failed`; уже существующая папка отклоняется до создания,
  одновременные создания одного имени идемпотентно дают один воркспейс;
- кнопка рендерится только когда деплой сконфигурировал `projectBase`
  (follow-фид несёт поле; внутренний devbim-деплой его не задаёт — кнопки
  там нет);
- персона сайта не показывает пользователю пути кэша, temp и
  attachment-хранилища: пользовательские файлы — только в папке проекта,
  выдача файла — создать его в рабочей папке и вызвать `present`.

Пространство проектов общее на весь сайт (вход по одному паролю, identity
нет): папки видны и создаваемы всеми вошедшими.

## Ограничения

Ограничения — на уровне UI: RPC-поверхность вошедшего браузера не ограничена
по принципалу (remoteAccess считает соединение owner); пароль — единственный
барьер. Для выдачи наружу держите пароль одноразовым и меняйте при передаче.
Отключения UI и набор инструментов агента — список строк в оверлее, правится
за одну минуту.

## Загрузка документов клиентом

В меню «+» рядом с полем ввода есть строка добавления файла: клиент
прикладывает к сообщению документ — PDF, Word (.docx), Excel (.xls, .xlsx)
или обычный текст (.txt, .md, .csv). Текст документа извлекается в браузере
в момент выбора файла и уходит агенту в том же сообщении отдельным блоком
рядом с файловым блоком; именно этот текст агент и читает — прочитать сам
исходный вложенный файл инструментом read агент может, только если это
обычный текстовый формат.

Лимиты закреплены в оверлее (строка `ui-conversation` в
`client-north-waterfront.patch.yml`): 25 МиБ на файл и 50 000 символов
извлечённого текста на документ. При выходе за текстовый лимит хвост
обрезается с пометкой об обрезке в блоке текста; агент предупреждает клиента
и просит недостающую часть обычным текстом.

Частые случаи:

- старый `.doc` в браузере не разбирается — сайт предлагает пересохранить
  файл как `.docx` и добавить заново;
- у сканированного PDF нет текстового слоя — текст не извлекается, файл
  прикладывается как есть, и агент видит только имя файла; фрагменты со
  скана просите клиента присылать обычным текстом.
