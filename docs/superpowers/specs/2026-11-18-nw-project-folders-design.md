# Дизайн: проекты клиентского сайта NW — папки проектов и spill вне Temp

Дата: 2026-11-18. Статус: утверждён пользователем; правка 2026-11-18 (этап плана): механизм гейтинга кнопки уточнён по факту исследования — поле `projectBase` в baseline follow-фида вместо «отсутствия неймспейса» (клиент монтирует все неймспейсы из сгенерированного артефакта независимо от хоста, поэтому отсутствие неймспейса не может быть сигналом), и глагол `createProject` живёт на существующем неймспейсе `workspace`.

## Контекст и цель

Клиентский прод `north-waterfront.dev-bim.com` (оверлей `packages/bundle/web-app/client-north-waterfront.patch.yml`, лаунчер `dsh-web-north-waterfront.cmd`) устроен так, что пользовательские артефакты размазаны по служебным местам, а «своей папки» у клиентского пользователя нет:

- Результаты `mcp__drawing5__*` крупнее 12 500 токенов (в основном `get_sheet_images`) spill-policy выгружает в `%TEMP%\dsh-spill-<6>\session-<12>\…` (`packages/spill/spill-local/src/store.ts:36-39`); модель видит путь в notice и может показать его пользователю. Это внутренний кэш восстановления контекста с 30-дневной очисткой, а не доставка.
- PDF-отчёты (`tool-pdf`) пишутся в cwd сессии — но cwd на NW-сервере это общий first-use воркспейс `<Documents>/deepseek-harness/default-workspace` (`packages/api/workspace-controller/src/default-directory.ts:77`), общий для всех клиентских пользователей.
- Лаунчер создаёт `%USERPROFILE%\north-waterfront`, но env `WORKSPACE` никто не читает — папка мёртвая. `directory-picker` на клиентском сайте отключён: клиентский пользователь не может ни выбрать, ни создать папку.

Цель — две возможности:

1. Всё пользовательское живёт в папке проекта под базой NW: сессии работают в своих проектах, файлы (`pdf_report`, вложенные папки) пишутся туда; spill остаётся внутренним кэшем модели, но уходит из `%TEMP%` в `DSH_HOME`, и модель не показывает пользователю temp/кэш-пути.
2. Клиентский пользователь создаёт проекты сам — кнопкой «Новый проект» в панели проектов: имя → папка `<база>/<имя>` → воркспейс → новая сессия в нём.

## Решения брейншторма

- Подход A — «фабрика проектов»: новый узкий seam в `workspace-controller` + кнопка в `ui-workspace` + wiring оверлея. Выбран: закрывает обе задачи, не расширяет доверенную поверхность, работает для любого деплоя.
- Вариант B — confinement (`root`) у `directory-picker-browse` и пере-включение пикера на NW — отклонён: пикер спроектирован для доверенных пользователей (крошки от корня диска, полный браузинг ФС сервера), его поверхность рискованнее расширять, чем добавить узкий глагол; UX — браузинг папок вместо «проект по имени».
- Вариант C — только overlay (`documentsDirectory` = база) — отклонён: даёт путь `<база>/deepseek-harness/default-workspace` и не даёт создавать проекты вообще.
- Пространство проектов общее: вход на сайт по одному паролю, per-user identity нет (вне области).
- База — `%USERPROFILE%\north-waterfront`, переопределяется `NW_PROJECTS_DIR` из `.env.north-waterfront`.
- UX создания — кнопка в панели проектов с вводом имени (не выбор при новой сессии, не оба).
- Пользовательские артефакты — только файлы в папке проекта; большие текстовые результаты инструментов НЕ сохраняются как файлы проектов (spill остаётся кэшем).
- Глагол создания — `@Remote('createProject')` на самом `WorkspaceController` (неймспейс `workspace`): отдельный дочерний контроллер отклонён на этапе плана — неймспейс `workspaceProjects` монтировался бы на клиенте из того же сгенерированного артефакта независимо от хоста, так что «отсутствие неймспейса» всё равно не работает сигналом, а отдельный контроллер требует ручной правки remotes-сборки без других выгод.

## Архитектура: компоненты

### 1. Хост: `@deepseek-ai/dsh-api-workspace-controller`

Конфиг (существующая схема `Config`):

| Поле | Ограничение |
|---|---|
| `projectBase` | абсолютный полностью определённый путь; валидируется как `documentsDirectory` (`validateDocumentsDirectory`). Взаимоисключим с `documentsDirectory`: оба заданы → ошибка на загрузке (misconfiguration fails loud) |

Глагол `createProject` на `WorkspaceController` (неймспейс `workspace`):

- `create({ name })` → валидация имени → `mkdir(join(projectBase, name), { recursive: true })` (база создаётся при первом использовании) → регистрация Workspace через существующий `commands.create` (заголовок = последний сегмент = имя) → проекция `WorkspaceCreateValue`.
- При незаданном `projectBase` глагол отказывает кодом `workspace/project-unavailable` (misconfiguration fails loud в момент вызова — на загрузке неотличимо от «не сконфигурировано намеренно»).

Капабилити-сигнал клиенту — поле в follow-фиде: baseline-кадр `WorkspaceBaseline` получает `projectBase: string | null` (null = возможность выключена). Существующий канал проекции воркспейсов; старый читатель игнорирует неизвестное поле, новый терпит отсутствие — безопасное same-version расширение.

`initializeDefault`: при заданном `projectBase` first-use каталог дефолтного воркспейса = `join(projectBase, DEFAULT_WORKSPACE_DIRECTORY)` вместо ветки Documents. Реестр по-прежнему не переносит уже созданный дефолт — существующие установки не меняют поведение.

### 2. Валидация имени проекта

Zod-refine по образцу `createDirectoryRequestSchema` плюс Windows-специфика. Инварианты, не настройки:

- после trim: непустое, 1–64 символа; Unicode разрешён («Жилой дом 12» валидно);
- запрещены `/ \ < > : " | ? *`, управляющие символы, `.` и `..`, точка или пробел в начале/конце (Windows молча срезает их);
- запрещены зарезервированные имена устройств без учёта регистра: `CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`;
- существующий каталог `<база>/<имя>` или воркспейс с этим путём → отказ `exists`.

Коды ошибок на проводе (семейство `workspace/project-*`): `workspace/project-name-invalid`, `workspace/project-exists`, `workspace/project-create-failed`, `workspace/project-unavailable`.

### 3. Клиент: `@deepseek-ai/dsh-client-ui-workspace`

- Кнопка «Новый проект» в `headerActions` браузера воркспейсов (`rows/WorkspaceBrowser.tsx`); рендерится только когда follow-фид принёс `projectBase !== null`.
- Диалог по образцу rename из `rows/WorkspaceDialogs.tsx`: поле имени (placeholder с примером), Enter — создать, Esc — отменить; под полем — локализованная ошибка по коду RemoteError (`project-name-invalid` / `project-exists` / общий — сытое сообщение).
- Успех: воркспейс приходит follow-фидом, переиспользуется существующее действие `startSession(workspaceId, { clearPreviousDraft: false })` — сессия создаётся и открывается.
- Копирайт — все 8 локалей `locales.ts` (zh — источник ключей, остальные `satisfies`), английский в sentence case, вход через `dsh-client-ui-ux`.

### 4. Оверлей NW и лаунчер

`client-north-waterfront.patch.yml`:

- same-id override `workspace-controller` (цель — строка `web-app/cordis.patch.yml:158`): `projectBase: !!js process.env.NW_PROJECTS_DIR ?? (process.env.USERPROFILE ?? process.env.HOME) + '/north-waterfront'` (`join`/`homedir` в `!!js`-контексте нет; `process.env` и конкатенация — санционированный паттерн этого оверлея);
- same-id override `spill-local` (цель — строка `base/cordis.patch.yml:421`): `root: !!js dshHomePath('spill')` — spill-файлы в `<DSH_HOME>\spill`, 30-дневная очистка (`cleanupPeriodDays`) без изменений;
- одна фраза в персону `preset-standard` и в `instructionsPrefix` `agent-preset-custom`: пути кэша, temp и attachment-хранилища никогда не показываются пользователю; пользовательские файлы — только в папке проекта; выдать файл = создать его в рабочей папке и вызвать `present`.

Лаунчер `dsh-web-north-waterfront.cmd`: `NW_PROJECTS_DIR` (по умолчанию `%USERPROFILE%\north-waterfront`, задаётся до загрузки `.env.north-waterfront`, чтобы файл мог переопределить; mkdir базы сохраняется); мёртвый env `WORKSPACE` убирается.

## Граничные случаи и обработка ошибок

- База не существует — создаётся `recursive` mkdir при первом проекте или first-use дефолте.
- База недоступна на запись / mkdir упал — `workspace/project-create-failed` с причиной; ничего молчного.
- Гонка двух созданий одного имени разрешается идемпотентно: `commands.create` семантически «create or resolve» над путём, оба вызова возвращают один и тот же воркспейс. Заранее существующая папка обнаруживается проверкой до mkdir и отказывается кодом `exists`.
- Существующий продовый `default-workspace` в Documents остаётся зарегистрированным воркспейсом: файлы на месте, панель его показывает. Авто-миграции нет; после деплоя оператор может переименовать его в UI или перенести вручную.
- Сессии без явного workspaceId продолжают попадать в дефолтный воркспейс (семантика `defaultCwd` не меняется) — на свежем деплое он окажется под базой.

## Безопасность

- Клиентский пользователь не получает браузинг файловой системы сервера: новый глагол создаёт ровно один сегмент под зафиксированной базой, traversal исключён валидацией.
- `projectBase` не расширяет права песочницы: `workspace-write` уже ограничен cwd сессии, cwd каждого воркспейса — его собственная папка.
- Имя — типизированное значение конфигурации от пользователя (как остальные значения форм сайта), а не свободный путь.

## Тесты и документация

- `workspace-controller`: матрица валидации имён (кириллица, reserved, `..`, крайние точки/пробелы, управляющие, длина), happy path `createProject`, коллизия `exists`, `create-failed`, `unavailable` без конфига, `initializeDefault` под `projectBase`, отказ при обоих конфигах, поле `projectBase` в baseline фида — при 100% пофайловом покрытии.
- `ui-workspace`: скрытие кнопки при `projectBase === null`, маппинг кодов ошибок на строки, успех → `startSession` в созданном воркспейсе; все 8 локалей (`verify-client-ui-i18n`).
- Доки: README `workspace-controller` (+README.zh.md и i18n-запись), `docs/config-catalog.md` (генерат `gen-config-catalog`), комментарии оверлея; `pnpm run doc-sync`.
- Снапшоты: keyless-сьюта NW-оверлей и персону не покрывает (проверено: в `snapshots/` нет ни одного сценария north-waterfront) — новый снапшот не требуется; строка персоны меняется только внутри оверлея, не в shipped-профилях.
- SDK не меняются: `SessionEventMap`, agent-loop и события сессий не затронуты.

## Вне области

- Per-user identity и личные пространства проектов.
- Авто-миграция существующего `default-workspace` в базу.
- Экспорт attachment-изображений отдельными файлами в проект (PDF уже встраивает их; отдельная задача при необходимости).
- Сохранение больших текстовых результатов инструментов как файлов проектов.
