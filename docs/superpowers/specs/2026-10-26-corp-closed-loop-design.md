# Дизайн: корпоративная ИИ-система в замкнутом контуре — этап 1

Дата: 2026-10-26. Статус: на утверждении пользователем.

## Контекст и цель

DeepSeek Harness — плагинный агент-харнесс (Cordis) с веб-GUI (`dsh web`), модель-пикером и расширяемым LLM-слоем. Цель — «из коробки» система для замкнутого корпоративного контура: без выхода в интернет, с корпоративными данными, где пользователь сам скачивает локальную модель из внутреннего каталога и сразу видит её в системе.

Решения брейншторма:

- Инференс — локально у каждого пользователя через Ollama (этап 1); центральный GPU-сервер — этап 2, отдельным проектом.
- Источник моделей — существующий внутренний файлсервер: GGUF-файлы + `manifest.json`.
- Корпоративные данные — файлы на сетевых шарах (UNC), внутренние веб-ресурсы, свои файлы сессии.
- Поставка — Windows-установщик (молчаливая установка для ИТ).
- Реализация — новые capability-плагины поверх harness; ядро и agent-loop не трогаем (правило репозитория «Plugins, not loop changes»).

## Архитектура: компоненты

### 1. Capability «model-registry»

Полный seam по конвенции репозитория (Service Definition / Provider / Consumer):

- `packages/llm/model-registry/` (`dsh-model-registry`) — Service Definition: состояния моделей (available / downloading / installed / update-available / failed), события прогресса, RPC-методы каталога и управления.
- Провайдер каталога в том же пакете (`dsh-model-registry-file`) — читает `manifest.json` с файлсервера (HTTP(S) URL, настраивается через settings-секцию), качает GGUF с проверкой SHA-256, регистрирует в Ollama (`ollama create <name> --file <modelfile>`), удаляет (`ollama rm`).
- `packages/client/ui-model-registry/` (`dsh-ui-model-registry`) — панель в настройках «Модели»: карточки (название, описание, размер, minRam, статус), кнопки «Скачать»/«Удалить», прогресс (проценты + скорость). Расширение UI — по существующему паттерну `dsh.client` + слот `settings.section` (как `ui-settings-models`).

Интеграция с модель-пикером — без нового LLM-кода: корпоративный профиль статически объявляет pi-ai-роут `ollama` (`api: openai-completions`, `baseURL: http://127.0.0.1:11434/v1`); установленные модели Ollama отдаёт по `GET /v1/models`, существующий discovery (`packages/llm/llm-pi-ai/src/discovery.ts`) автоматически показывает их в пикере (`session.modelCatalog`, `packages/client/ui-model-selection`). После установки/удаления модели реестр триггерит обновление каталога (событие `llm/adapters-updated` или перечитка discovery).

### 2. Интранет-fetch провайдер

`packages/web/web-fetch-intranet/` (`dsh-web-fetch-intranet`) — реализует существующий интерфейс fetch-провайдера capability `web` (`registerFetchProvider`); выбирается существующим конфигом `fetchProvider`. Конфиг — allowlist зон; каждая зона задаёт DNS-суффикс и, опционально, список CIDR. Проверка: хост совпадает с суффиксом зоны; если у зоны заданы CIDR — все DNS-ответы хоста обязаны попасть в них; иначе отказ с перечнем разрешённых зон. Публичный `web-fetch-http` в корпоративном профиле не монтируется.

### 3. Корпоративный бандл и профиль

`packages/bundle/corp/` (`dsh-corp`) — `cordis.patch.yml` поверх `dsh-web-app`: pi-ai-роут Ollama, `fetchProvider: intranet`, model-registry, интранет-провайдер, fs-политика (read-only корни сетевых шар настраиваются в UI сессии), settings-секции по умолчанию (URL файлсервера, allowlist зон). Установка — поддерживаемый путь `dsh plugin --profile <name> add <package>`; установщик сеет профиль `corp` в `$DSH_HOME/profiles/corp` (манифест + `cordis.patch.yml` по паттерну `initProfile`, `packages/boot/app-boot/src/profile.ts`).

### 4. Windows-установщик

`scripts/installer/` (Inno Setup). Молчаливая установка для ИТ: bundled Node-runtime, собранный harness (lib/), Ollama (официальный silent-установщик, закреплённая версия), профиль `corp`, автозапуск Ollama, ярлык «Корпоративный ИИ» → `dsh --profile corp web`. Веб-GUI слушает только `127.0.0.1` (по умолчанию; доступ коллегам — опционально отдельным patch-слоем или reverse-proxy, в установщик не входит).

## Потоки

### Скачивание модели

1. Открытие панели: провайдер качает `manifest.json` (кэш ~5 минут; офлайн — последний успешный с бейджем «офлайн-каталог») и опрашивает Ollama `GET /api/tags` (health-check).
2. Клик «Скачать»: проверка свободного места против `sizeBytes` → скачивание GGUF во временный каталог (прогресс-события в UI; докачка HTTP Range при поддержке, иначе с нуля) → проверка SHA-256 → `ollama create` → удаление временного файла.
3. Успех → обновление модель-пикера, модель выбирается в сессии.

Схема манифеста (версия 1, поле `version: 1`):

```json
{ "version": 1, "models": [ { "id": "qwen3-14b", "name": "Qwen3 14B", "description": "...", "version": "1.0.0", "ggufUrl": "https://files.corp.local/models/qwen3-14b-q4.gguf", "sha256": "...", "sizeBytes": 8589934592, "modelfile": "FROM ./qwen3-14b-q4.gguf\n...", "minRamGb": 16 } ] }
```

Админ ведёт манифест вручную или скриптом; GGUF и Modelfile лежат рядом на файлсервере.

### Корпоративные данные

- Свои файлы — штатная рабочая папка сессии.
- Сетевые шары — в настройках сессии пользователь указывает разрешённые UNC-корни (например `\\fileserver\docs`); они становятся read-only корнями fs-политики сессии. Запись на шару — отдельный опциональный переключатель, по умолчанию выключен. UNC-пути поддерживаются fs-политикой без доработок (лексическое сравнение путей + `realpathSync.native`).
- Внутренние веб — `web_fetch` через интранет-провайдер (allowlist зон, см. выше).

### Гарантии замкнутого контура

- LLM — только `http://127.0.0.1:11434/v1` (зашито в профиль).
- Поисковые провайдеры — не настроены (отсутствуют конфигурационно).
- `fetchProvider: intranet`; публичный fetch-провайдер не монтируется.
- Телеметрии наружу нет; proxy-переменные окружения установщиком не задаются.
- Модели и манифест — только внутренний файлсервер.
- Worker-потоки (модельные скрипты) наружу не пойдут: в контуре нет маршрута; прокси им по дизайну не передаётся.

## Обработка ошибок

Принцип — «misconfiguration fails loud» с внятной причиной, не пустое состояние:

- Файлсервер недоступен: офлайн-каталог из кэша, кнопка «Скачать» неактивна с указанием причины.
- SHA-256 не сошёлся: временный файл удалён, статус «файл повреждён» + «Повторить».
- Мало места: отказ до старта скачивания.
- Ollama не запущен: красный статус панели + кнопка «Запустить».
- `ollama create` упал: stderr Ollama в карточке.
- `web_fetch` вне allowlist: отказ с перечнем разрешённых зон.
- Битый манифест (schema-невалиден): явная ошибка панели, не пустой список.

## Тестирование

- Юнит: парсинг/валидация манифеста, проверка SHA-256, логика allowlist зон (DNS → CIDR).
- Поведенческие: провайдер каталога против локального mock-файлсервера (новый `test-support/fileserver-mock` по паттерну `llm-mock-server`).
- Установка/удаление модели — с реальным Ollama, самопропуск если Ollama отсутствует.
- UI-панель и модель-пикер — keyless снапшоты веб-GUI (по политике репозитория).
- Интеграционные точки (settings-секция, RPC) — фокусные тесты capability seam.

## Этапы

1. Каталог и установка моделей: model-registry + UI-панель + pi-ai-роут Ollama. Инкремент полезен при ручной настройке.
2. Данные: интранет-fetch + настройка UNC-корней в UI сессии.
3. Из коробки: бандл `corp`, профиль, Windows-установщик.
4. Этап 2 (отдельный проект): центральный GPU-сервер как второй источник моделей; права доступа к моделям.

## Ограничения и риски

- Windows ACL-раннер песочницы может не применить ACE на SMB-шаре; для read-only-корней некритично, документируется как ограничение.
- LAN-доступ к веб-GUI (0.0.0.0) — CLI `dsh web` намеренно отклоняет; при необходимости доступ коллегам — reverse-proxy или patch-профиль, вне установщика по умолчанию.
- Версия Ollama закрепляется в установщике; обновление Ollama — через перевыпуск установщика.
- Манифест не поддерживает права «кому какие модели» — этап 2.
- Подчинённые (subagent) сессии в текущем UI не выбирают модель — ограничение harness, не блокирует этап 1.
